# ATLOB ERP de escritorio para Windows

El instalador y el portable se generan para Windows x64. Ambos abren el asistente de conexión a PostgreSQL y comparten la configuración cifrada del usuario de Windows. El portable se puede copiar y ejecutar en una carpeta independiente. PostgreSQL es un servicio externo a la aplicación.

1. Inicia el servicio de PostgreSQL local. Prepara una base y un rol de aplicación con permiso de conexión (sin privilegios de superusuario ni `BYPASSRLS`, pues `server.ts` verifica `pg_roles` y rechaza roles privilegiados con `PG_ROLE_UNSAFE`). Para una base nueva, el rol necesita permisos `CONNECT` y `CREATE` sobre la base y el esquema `public`.
2. Abre el instalador o el portable (`desktop/electron-builder.yml`, `appId: pe.atlob.erp`). La pantalla de conexión (`desktop/config.html`) propone por defecto `localhost`, puerto `5432`, base `sistema_contable` y usuario `contabilidad_app`; introduce la contraseña (y ajusta base/usuario si corresponde). La casilla de autorización para crear tablas solo se habilita cuando la base indicada es distinta de `sistema_contable` y `atlob_test`. Ante cualquier inconveniente, el asistente informa diagnóstico, causa probable y acción sugerida.
3. En una base nueva autorizada (marcando la casilla de preparación automática o con `ATLOB_DESKTOP_MIGRATE=1`), el migrador aplica las **21 migraciones** de `MIGRATION_FILES` (`server/db/migration-files.ts`); sobre `sistema_contable` arranca estrictamente en modo verificación de solo lectura (`verifyOnly`). En una base recién preparada, la pantalla única de bienvenida registra el estudio y la cuenta titular (`ADMINISTRADOR`), carga catálogos y semillas en transacción, activa una licencia local de evaluación (`max_usuarios = 3`) e inicia sesión hacia la cartera de empresas. La verificación en dos pasos (2FA / TOTP) es opcional (`mfa_requerido = false` por defecto) y puede activarse o desactivarse en cualquier momento desde **Herramientas › Usuarios y permisos**.
4. Al cerrar la ventana, el proceso principal solicita el apagado ordenado (`{ type: 'shutdown' }`, espera máxima de 2 segundos antes de forzar cierre) y detiene el subproceso servidor y el pool PostgreSQL. Al reabrir, recupera la conexión cifrada de `instalacion.bin` y vuelve a pedir inicio de sesión.

El subproceso servidor (`desktop/generated/server.mjs` vía `utilityProcess.fork`) escucha en un puerto efímero que asigna Windows en `127.0.0.1` y rechaza con HTTP `403` peticiones cuyo `Host` u `Origin` difiera de ese origen local. Además, el aislamiento explícito del entorno en `desktop/main.cjs` mantiene desactivada por defecto la bandera opcional `ATLOB_BLOQUEAR_MEMORIA` para no interrumpir flujos de escritorio salvo solicitud explícita. Las ventanas `BrowserWindow` corren con `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true`, `devTools: false`, bloqueo de apertura de ventanas externas, navegación restringida y permisos de sesión denegados. El proceso principal espera confirmación en `/api/health` (`status: 'UP'` y `database: 'POSTGRESQL_CONNECTED'`) antes de cargar la interfaz; un fallo de conexión devuelve al asistente con diagnóstico y opción de reintento.

Los cinco secretos y la conexión se guardan con DPAPI (`safeStorage`) en `instalacion.bin` dentro de `app.getPath('userData')` (`%APPDATA%`). El archivo depende del perfil de Windows que lo creó. Una instalación nueva genera claves aleatorias propias (32 bytes / 64 dígitos hex cada una). El uso de una base que contenga credenciales SUNAT o respaldos cifrados con claves anteriores requiere resolver primero la continuidad de esas claves. [Almacenamiento seguro de Electron en Windows](https://www.electronjs.org/docs/latest/api/safe-storage)

Los ejecutables se generan sin firma (`forceCodeSigning: false` y `signAndEditExecutable: false`). Windows SmartScreen puede mostrar una advertencia. La firma y su verificación quedan pendientes.

`npm run desktop:dev` inicia la variante de escritorio desde el repositorio. `npm run dist:win` (`desktop/prepare.ts --win`) compila interfaz y servidor, empaqueta `app.asar` con `desktop/generated/**` en `asarUnpack`, ejecuta automáticamente la auditoría `verify-package.ts` vía `desktop/after-pack.cjs` y genera ambos ejecutables en `release/`. `npm run desktop:verify` re-ejecuta `desktop/verify-package.ts` sobre `release/win-unpacked/resources/app.asar` (y su carpeta `app.asar.unpacked` asociada). Para uso normal basta abrir uno de los ejecutables.

## Plan de integración de RLS y claves foráneas

La conexión de escritorio a `sistema_contable` verifica las **21 migraciones** registradas en `MIGRATION_FILES` dentro de una transacción de solo lectura (`verifyOnly`). El plan siguiente requiere aprobación antes de cambiar el migrador oficial o aplicar las nuevas etapas en esa base.

| Orden propuesto | Trabajo | Evidencia previa al despliegue |
|---|---|---|
| 1 | Mantener las **21 migraciones** y sus hashes (con tolerancia a LF/CRLF en `migrate.ts`). Añadir entradas versionadas para las FK `01_contabilidad`, `02_comprobantes`, `03_cartera`, `04_tesoreria`, `05_planillas`, `06_tributos` y `07_sire` (`75` relaciones en el catálogo). | Ejecutar `diagnosticoFkEmpresa.ts` sobre la base vigente (`81` tablas registradas en `REGISTRO_DATOS_EMPRESA`) y detenerse ante huérfanos o cruces. Confirmar las acciones de borrado y las claves de las tablas hijas. |
| 2 | Convertir las reglas de `seguridadRls.ts` (`41` tablas en etapas `5.1`, `5.2a`, `5.2b`, `5.2c` y `5.3`, adicionales a las `23` tablas con RLS base en migraciones = `64` tablas con RLS) en migraciones oficiales ordenadas. | Verificar aislamiento entre dos empresas, acceso sin contexto, membresía revocada, login, renovación y trabajos con `contabilidad_app`. |
| 3 | Probar el mismo migrador en una base de pruebas vacía y en una copia de pruebas con las **21 entradas existentes**. | Comparar catálogo, políticas activas, `FORCE RLS`, claves validadas, hashes del registro y repetición sin cambios. Probar un fallo intermedio y la reversión de la etapa. |
| 4 | Programar el cambio sobre la base existente tras aprobación, respaldo verificado y una ventana de mantenimiento. | Revisar tiempos y bloqueos. Ante un error, revertir la transacción de esa etapa. Mantener una restauración verificada para recuperar un estado anterior a etapas ya confirmadas. |

El migrador de una base nueva aplicará las etapas en el mismo orden que la actualización de una base existente. La prueba de escritorio actual usa el esquema base y la suite de PostgreSQL aplica las etapas adicionales en transacciones que se revierten. [Políticas RLS](https://www.postgresql.org/docs/18/sql-createpolicy.html) · [Validación de restricciones](https://www.postgresql.org/docs/18/sql-altertable.html)
